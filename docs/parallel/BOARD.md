## Decisions (defaults applied so work can continue)

| ID | Question | Decision | Basis | Override |
| --- | --- | --- | --- | --- |
| D-1 | Which run outcomes block administrative completion? | `blocked`, `failed`, `inconclusive`, `cancelled` | Owner decision, 2026-10-25 | none needed |
| D-2 | A verified run is linked to the task but not accepted | Refuse administrative completion; use `accept_task_run`. Built into the patch. | Default. Keeps provenance accurate. `accept_task_run` is always available, so nothing dead-ends. | edit this row |

Refusing would leave an abandoned failed child with no exit, so its parent could never complete. The waiver stays reasoned and visible in the record. | edit this row |
| D-4 | Both providers unavailable for transport, install or authentication reasons (CC-05 R14) | Block and report upward. Do not queue silently. | Owner policy, 2026-10-25 (below). The routing function returns Block with `NoEligibleProvider`; escalation is the Overseer layer's job (CX-08). | edit this row |

**Owner policy on escalation (2026-10-25, applies to both lanes).** This is a working team with the Owner in charge, not a policy of keeping the Owner out of the loop. A task that stops or fails goes up the hierarchy. Project Managers handle what they can; Workers report up. A blocker stays visible: anyone looking at the board can see what blocked the task and why. Items that need the Owner go to the Main Overseer, and the Overseer brings them to the Owner. Items that the team can resolve are handled among the agents without Owner interaction, and they are still visible. Escalation is about who acts, not about hiding information from the Owner. Serious failures reach the Owner directly through the Overseer.
