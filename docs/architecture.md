## System boundary

M40 implements the local background dispatch path: one short MCP call queues independent prepared roles, returns immediately, and lets the background dispatcher submit each Codex turn without waiting for completion. M41 binds one logical Main thread and routes new actionable PM events to Main, Main reviews back to the affected PM, and local Owner decisions through Main to that PM. Routine progress stays passive. Normal MCP startup starts no Codex app-server and opens no window; the hidden server starts only when queued work needs dispatch. Its process-level config disables the user's other globally configured MCPs, while each role thread receives only its scoped Cathulu MCP config. Missing role tools, invalid config, and unapproved server requests fail closed. The dispatcher is enabled by default in the matched build; set `CATHULU_ROLE_DISPATCHER_ENABLED=0` to disable it. Live provider/account, role workspace, visible thread ownership, restart/concurrency, and real parallel-work behavior still require validation after the owner reloads Codex. See accepted ADR-0016, ADR-0018, and PLAN-015.

```text
Owner
  ↕ conversations, commands, approvals
Codex app / Main Overseer
  ↕ local MCP (domain reads and state transitions)
Cathulu Core ───── local SQLite database
  ├─ project, objective, task, and run state
  ├─ structured delegation packets and lifecycle evidence
  ├─ append-only event, decision, QA, and workflow history
  ├─ managed memory lifecycle over domain records and evidence
  ├─ Git reconciliation
  └─ local telemetry normalization and context-transfer ledger
       ↕ read-only query boundary (M1 dashboard)
Tauri desktop app / React UI
```

Codex owns model/tool execution, shell, Git edits, worktrees, and code changes; Cathulu owns the logical hierarchy, durable role memory, task dispatch, event routing, approvals, and evidence. Main has a global read/review/coordination capability and a read-only Codex sandbox; it cannot implement project work or dispatch Workers. Each PM/Worker turn receives a short-lived, hashed, assignment-scoped Cathulu capability. The local dashboard records an explicit Owner approve/decline decision but never executes the approved operation. The local app-server is now the role execution transport; it uses Codex as the reasoning and execution harness. Project-scoped role prompts and thread-level tool checks fail closed when required Cathulu tools are absent. A future Cathulu selector surface is separate from this dashboard and is defined in ADR-0002. The local MCP server exposes domain resources and semantic operations; it never exposes SQL or table CRUD.

M26 established matched release binaries for MCP and the read-only desktop dashboard. ADR-0020 now separates their lifecycles: starting MCP starts no desktop or terminal window. The Owner starts the matching desktop or terminal monitor explicitly when desired. The desktop release uses Tauri's `custom-protocol` feature to serve its bundled frontend rather than depending on a running Vite development server. MCP stdout remains dedicated to its protocol.

The optional specialist-model layer in ADR-0007 is an optimization boundary inside the local Cathulu control plane. Deterministic Cathulu code handles exact facts and rules. A DecisionModel may make bounded, typed choices; a ContextModel may extract or reduce selected existing information. Both default to disabled, and the same baseline workflow remains available without either. Codex remains the primary reasoning, coding, planning, debugging, and user-interaction system. These specialist interfaces do not run agents, replace Codex model/effort selectors from M9, or change deterministic QA authority.

### Bounded project-agent hierarchy

ADR-0009 defines the role boundary: one logical Main Overseer coordinates and never implements project changes; one Project Manager may own each active project assignment; each PM may dispatch at most two implementation workers. Before PM dispatch, Main prepares a separate outcome-focused workflow brief per project. Each PM decomposes its brief into bounded Worker tasks and reviews the Worker evidence; Main reviews the PM plan/result against the brief and supporting evidence. Escalations travel Worker → PM → Main → Owner, and only actions beyond the upper roles' authority reach the Owner. Owner-required actions surface immediately and pause only their affected project. These reviews do not replace deterministic QA. Chats are replaceable representations of persistent logical roles, with one globally bound Main thread and one binding per project/assignment; a replacement chat can occupy the same logical seat. M21 verified one nested PM → Worker chain, not independent no-wait dispatch. M40 adds a default-on local app-server dispatcher, SQLite lease/outbox, scoped PM/Worker capabilities, and dashboard queue state. M41 adds Main event binding and selective, idempotent inbox delivery for PM plans/results, escalations, and Owner decisions. An Owner decision returns through Main to only the affected PM; the dashboard records intent and does not run the requested operation. Schema-v17 begins routing at the migration-time event cursor so earlier events are not replayed. The active project workspace and real Codex UI/thread ownership remain live validation items. See the [agent operating contract](agent-operating-contract.md), [ADR-0016](decisions/ADR-0016-event-driven-role-orchestration.md), [ADR-0018](decisions/ADR-0018-local-owner-action-decisions.md), and [PLAN-015](plans/PLAN-015-event-driven-role-orchestration.md).

This hierarchy is separate from Phase 4 M10's evidence-gated cross-project scope/Sub-Overseer work. The current focus is independent project tasks; no cross-repository edge or handoff is inferred. Schema 11 records nested parentage, one active PM assignment per project, the two-worker total per assignment, and pre-dispatch memory activation evidence. Schema 12 makes Main/PM role identity and stable memory/tool-profile bindings explicit. New PM retrieval and activation must use the role's stable receiver scope; dispatch rechecks it. Existing activation receipts remain immutable historical evidence. Repeated Main and PM activations reuse the role receiver scope so unchanged knowledge is not resent. PLAN-006 and PLAN-008 record existing implementation and runtime limits. Native nested spawning and inherited Cathulu MCP access were observed in M21, but that probe did not test independent async role threads. The current matched build adds the dispatcher and event-driven role turns; the active MCP still needs to reload it before this behavior is live.

M21 observed one Project Manager spawning one Worker and confirmed that Main, PM, and Worker could reach Cathulu MCP. The available memory tools differed: the PM could read `cathulu://dashboard` but did not have `read_memories`, while the Worker did. HOT/WARM memory was empty, and the run recorded “no relevant memory”; the current `prepare_context_transfer` operation cannot encode an empty transfer because it requires a memory ID. No hook event or parent-child telemetry edge surfaced, so the dashboard must continue to show hook coverage/relationships as unknown until observed. See the M21 evidence and the M22-M24 follow-up criteria in PLAN-006.

## Data and transaction model

SQLite is the source of truth. Use relational columns for projects, dependencies, objectives, tasks, decisions, workflow identities/versions, runs, quality checks, delegation identity/lifecycle, worker reports and review history, memory lifecycle metadata, and state needed for filtering. Use bounded JSON for typed delegation packets, worker reports, and heterogeneous event payloads. Each important transition appends its domain event and updates the corresponding current-state projection in one transaction. Decisions, workflow versions, delegation identity/packet content, report bodies, and delegation reference links are immutable; report reviews are append-only. Only a delegation's validated lifecycle status may change. Artifacts are stored as local references and hashes where possible, not copied into packets.

The initial data path is an OS-local application data directory. SQLite is configured for transactional writes and WAL. Startup runs additive database migrations and rejects databases newer than the app. Desktop startup opens the store and schedules one Git reconciliation pass on a blocking worker after the Tauri state is available; MCP startup does not duplicate that full scan. The explicit `reconcile_project` tool refreshes one project. Git HEAD changes deterministically invalidate only memory records whose freshness basis names that project. M11 records the current validated Graphify snapshot identity per project and invalidates only memories whose freshness basis explicitly names a replaced or unavailable graph snapshot. The memory layer stores distilled knowledge and source references; it does not duplicate current project, decision, workflow, run, or artifact state.

### Optional specialist-model optimization (M15-M17 foundations and M18a adapters implemented; first live shadow integration run recorded)

Use the least powerful mechanism that can safely answer a step:

1. Deterministic Cathulu code for exact facts, checks, rules, freshness, and state.
2. A DecisionModel for a bounded judgment over a versioned set of outputs.
3. A ContextModel for classifying, extracting, compressing, or summarizing selected existing information.
4. Codex for open reasoning, implementation, planning, debugging, synthesis, and ambiguous investigation.

M15 defines versioned, provider-neutral DecisionModel and ContextModel contracts with disabled implementations. DecisionModel inputs are bounded structured state built from authoritative Cathulu records, not whole repositories or transcripts. Decision responses carry schema versions and support explicit escape outcomes such as unknown, insufficient_context, needs_codex, needs_more_evidence, and not_applicable where appropriate; later shadow adapters must validate outputs and never accept executable actions. Confidence or probabilities describe the model response; they do not establish truth. ContextModel outputs are candidate projections with artifact ID/hash and source-span references, and retain the original raw artifact for audit and recovery. A model-generated summary never replaces SQLite state, Git, Graphify, tests, or raw evidence.

M16 adds fixed, versioned outcome schemas for workflow class and delegation strategy, including explicit escape choices. Its routing-state projection reads only bounded run, task-status, project-change-count, QA-count, and active-delegation fields from SQLite; it excludes task text, paths, run summaries, artifact contents, memories, and transcripts. The local shadow-trial boundary validates responses, records invocation metadata in the existing event ledger, and never returns a routing action to execution. A separate post-run review event can link a human counterfactual assessment to final run and QA evidence. This is test-double infrastructure, not evidence of specialist-model value.

M17 adds a bounded extraction shadow path for registered local test, compiler, CI, and tool-output artifacts. The loader checks the artifact hash when present, preserves the raw file, selects error-adjacent byte spans, and gives the local ContextModel only selected text and a stable Cathulu resource reference; it does not expose the filesystem path. Candidate output must match the requested artifact hashes and exact source bytes, fit the versioned schema and output bound, and retain verifiable spans. Invocation metadata and a separate result event use the existing append-only run event ledger. Remote configurations and empty input are skipped, and shadow results cannot change context delivery, QA, or success. M17 adds no migration, provider adapter, frontend change, or live call. Test doubles and a locally captured Rust test failure validate mechanics only; model quality and workflow value are unmeasured.

M18a adds optional Jev and ScaleDown HTTP adapters behind the provider-neutral interfaces. Jev receives only the bounded SQLite-derived routing projection and fixed outcome schema. ScaleDown receives only selected test/compiler/CI/tool-output excerpts after best-effort masking of credential labels and known token formats; source paths, task text, and artifact identifiers are excluded. Returned extraction offsets are checked against exact local source bytes, and candidates overlapping masked bytes are discarded. Requests occur only when a run explicitly enables the relevant capability in shadow mode, opts into remote data, and has a local key. Missing keys and provider failures are recorded as skipped/failure telemetry and do not block the run. The public MCP integration test exercises both shadow tools with credentials removed and an explicit nonexistent env-file path; it verifies immutable run/QA state and raw-artifact preservation. ScaleDown's reviewed API pages do not state a request-retention period, so remote transmission remains a per-run owner choice. No live call or provider-quality result is claimed by local checks.

M37 makes project-memory capture part of the run lifecycle. The first analyzed project run must establish an accepted, source-backed canonical summary; every later run records accepted memory IDs or a fixed `no_durable_change` reason code before finalization. This prevents empty scopes from silently persisting after project work. The receipt contains no free text, and memory bodies remain in the existing SQLite memory model. M38 added initial source-based profiles for the five registered projects and a global project-independence constraint. Jev may classify bounded candidates and the Context Model/CDM (including ScaleDown) may draft extractions in later experiments, but neither is required or authoritative; no specialist inference was invoked for the onboarding.
Each capability has an independent enabled flag and shadow/active mode; the effective state is disabled when the flag is false. All flags default to false, with optional per-workflow overrides captured in the immutable `run_started` event. M15 records run treatment and deduplicated invocation metadata in the existing append-only event log; no schema migration was needed. Invalid optional configuration falls back to an all-disabled treatment so it cannot block a run. Active treatment is rejected until the shadow stage passes its declared schema, privacy, fallback, and quality checks, a controlled comparison is pre-registered, and the owner explicitly approves the reversible pilot. Shadow predictions are recorded but cannot affect routing, memory, context delivery, QA, or deletion. A provider error, timeout, invalid response, or unavailable model skips the optimization and continues the current deterministic/Codex workflow.

Remote providers are an explicit egress exception to the local-first architecture. They require owner configuration and visible run attribution. Send only the minimum bounded decision fields or selected source spans needed for a capability; do not send full source trees, secrets, raw Cathulu memory, complete transcripts, or entire artifact stores by default. Credential masking covers common labeled values and known token formats but cannot guarantee detection of every secret; the owner must review selected evidence and explicitly allow remote processing for each run. Jev and ScaleDown adapters are optional, shadow-only, and disabled by default. ScaleDown request-retention terms were not found in the reviewed API docs. Active routing, success, QA, and memory authority remain unchanged.

Specialists may help rank memory candidates only after deterministic SQL/FTS, Graphify, or exact retrieval, deduplication, known-by filtering, freshness validation, and supersession checks have narrowed the set. They must not scan the whole archive. Results resolve to authoritative SQLite records and still pass scope and HOT-budget rules. Specialists cannot own memory, silently promote policy, delete evidence, declare security or correctness, or mark a run successful. Deterministic quality gates remain final. Provider integrations should use a small static capability registry and typed adapters, not a general plugin runtime. The M9 Codex model/effort settings continue to control Codex configuration only; specialist provider configuration is separate and does not change the active Codex model or effort.

### Codex-native delegation records

M6 adds an additive v5 delegation schema that links each record to one project, task, and matching running or blocked run. The typed v1 task packet is limited to 16 KiB and contains an objective, acceptance criteria, constraints, repository-relative allowed paths, current memory/artifact IDs, and requested report fields. Packet content is normalized before hashing. Memory references must be accepted, current, and visible to the same project/task scope. Artifact references must be available and associated with the parent run or unscoped; foreign-key links keep those artifacts from being collected as orphaned evidence.

The stable delegation ID and packet identity persist in SQLite. Idempotency keys and optional external correlation values are SHA-256 hashed; their raw values are not stored. Requested model and effort are stored separately, and effective values remain absent until a trusted source exists. `prepared`, `dispatched`, and `cancelled` are audit states; dispatch records an owner action through native Codex and does not prove that a worker started or completed. Status transitions append events in the existing journal, and the parent run's quality state is unchanged. The current MCP exposes semantic prepare/transition tools and `cathulu://delegations/{id}`; it does not spawn agents, run tools, create/move/remove/merge worktrees, or write Codex configuration. PLAN-015 proposes managing Codex role-thread lifecycle through the local app-server, subject to M36 validation.

M7 adds an additive v6 schema with one immutable, schema-v1 worker report (maximum 16 KiB) per dispatched delegation. Reports contain a summary, one of `completed`/`partial`/`blocked`/`failed`, changed repository-relative paths, commit IDs, worker check claims, blockers, and parent-run artifact/quality-check references. Changed paths must match the packet's allowed scope. Artifact references must be available and attached to the parent run; quality-check references must belong to that run and retain an immutable status/details-hash snapshot. Report and review submissions are idempotent, and only hashes of idempotency keys are stored.

Review decisions are append-only and produce `reported`, `accepted`, `rejected`, or `needs_follow_up` as the current review projection. Worker claims and review status do not change parent-run state or substitute for its mandatory quality checks. Report artifact links protect evidence from orphan collection. The MCP resource includes report and review history; the read-only dashboard shows the ten most recently active delegation records with the parent-run status and explicitly labels worker outcomes as claims.

M8 adds additive schema v7 for a captured delegation base commit, the latest verified linked-worktree snapshot, and privacy-minimized Codex subagent hook metadata. A new delegation captures the actual registered repository HEAD at preparation time; migrations leave older baselines unknown rather than infer them. Reconciliation accepts only an existing worktree listed by the registered repository, distinct from its registered root, and sharing its Git common directory. Cathulu reads HEAD, branch, cleanliness, and base-to-worktree paths; it never creates, moves, removes, or merges worktrees. Git verification checks worker-reported commits against the baseline and observed HEAD, and reported paths against the observed change set. Results are `verified`, `mismatch`, `unavailable`, `no_report`, or `no_claims`; a mismatch remains evidence and never accepts the report or changes parent-run quality. The stored local worktree path is not returned to the resource or dashboard; the path hash is used for display correlation.

Only `SubagentStart` and `SubagentStop` are added to the M3 hook allowlist. Cathulu records them only when the parent session/turn already maps to a run. Raw session and agent IDs are hashed, while coarse agent type and the documented active model slug are retained. A worker is associated with a delegation only through an explicit reference to a recorded start event whose run matches the delegation; later events then use the same hashes. Requested model/effort remain separate from observed model; effective effort is unknown because the hook contract does not expose it. Transcripts, prompts, tool bodies, and last assistant messages remain excluded. See [ADR-0005](decisions/ADR-0005-codex-worker-telemetry-and-worktree-verification.md).

### Hierarchical role-work gates (schema v13)

The local SQLite lifecycle records Main's immutable workflow brief per project/run, the PM's immutable Worker plan, and append-only parent reviews. `prepare_delegation` rejects PM assignments without the Main brief and Worker assignments without an accepted PM plan; a Worker packet must match the exact approved task key and packet. Worker reports are accepted by their PM, PM reports by Main, and PM result submission/closure is blocked while child reports, escalations, or owner requests remain unresolved. PM requests can be raised to Main; an explicit owner-approval request is available only for an unresolved PM escalation. Only the local desktop UI can record an Owner approval decision. The MCP no longer exposes a model-callable decision tool; the UI confirms the exact request hash and writes an append-only decision with its origin. Recording approval resolves only that keyed escalation and never executes the requested operation.

These are durable workflow-order and evidence gates. Ordinary MCP calls do not authenticate a Codex chat identity, so `reviewer_role` and other acting-role declarations cannot prove which chat invoked a tool. Dispatcher-created role threads receive short-lived scoped capabilities; those tokens constrain the role/project/assignment tool surface. The gate prevents accidental ordering violations but is not a boundary for unscoped calls outside the dispatcher. The local UI does not run the requested action. The default-on dispatcher routes new events to Main and affected PMs, while live app-server/tool parity and restart/concurrency behavior remain to be confirmed after reload. See [PLAN-015](plans/PLAN-015-event-driven-role-orchestration.md) and [ADR-0016](decisions/ADR-0016-event-driven-role-orchestration.md).

### Managed memory lifecycle

Cathulu manages knowledge through **experience → evidence → extraction → candidate → consolidation → durable knowledge**. Raw evidence is not permanent agent memory by default. Durable knowledge is a distilled, content-hashed record with provenance; no model-generated summary replaces its sources or the authoritative domain record it describes.

Memory class and temperature are independent dimensions:

| Class | Meaning | Typical use | Usual temperature |
| --- | --- | --- | --- |
| `working` | Current context needed by a logical scope | Objective, blockers, active constraints | HOT |
| `canonical` | Durable, accepted knowledge | Decisions, facts, contracts, procedures, lessons | HOT when active; otherwise WARM or COLD if superseded/historical |
| `episodic` | Reusable historical experience | Incidents, migrations, outcomes, failure patterns | WARM; HOT when strongly relevant; COLD after inactivity |
| `evidence` | What happened and its supporting artifacts | Run events, check results, diffs, bounded logs | COLD |
| `aggregate` | Compact statistics derived from multiple observations | Workflow and memory-policy outcomes | WARM |

Temperature is retrieval policy, not storage class. `hot` is in the small activation set for a scope; `warm` is selectively retrieved; `cold` is excluded from automatic context and opened for provenance, debugging, audit, or evaluation. A temperature transition updates the same stable record; it does not duplicate or erase it. Classes describe the information and are not inferred from temperature.

Existing domain entities remain authoritative. Memory metadata may point at an objective, decision, workflow version, run, check, or artifact, but must not mirror that entity's mutable state or create a competing copy of its meaning. A distilled canonical or episodic record is a separate knowledge claim and must link to the evidence and events that support it. Current project/Git state stays in its domain tables; exact state is read from SQLite, not semantic search.

Memory is a required project-context workflow, not a passive store. On the first analyzed project run, the Project Manager establishes a concise canonical `summary` from inspected repository sources and verified facts. At every project-run closeout, it records accepted memory IDs or an allowed fixed reason code for no durable update. Cathulu does not finalize a project run without this review, and it does not allow a no-update review while the project has no current canonical summary. The receipt contains only the disposition, fixed reason code, and memory IDs; knowledge bodies remain in the existing memory records with provenance. Source-based capture must never copy chat transcripts, private reasoning, or raw tool histories. See [ADR-0017](decisions/ADR-0017-project-memory-capture.md) and [PLAN-016](plans/PLAN-016-project-context-capture.md).

Memory records need stable IDs and content hashes; class, temperature, kind, and scope; created/updated times; optional validity bounds; supersession links; importance, evidence confidence, reuse count, and last-use time; freshness bases such as repository commit, contract hash, dependency snapshot, or graph snapshot; and source-event and artifact references. Global scopes and project/objective/task scopes use stable domain IDs. A future logical agent scope can use a stable opaque scope ID without creating another project/decision/run authority. Confidence represents strength/quality of evidence, not a model's confidence score. Provenance may point to source files and commits, test results, accepted decisions, contracts, Graphify snapshots, runs, artifacts, command results, and human instructions. Canonical memory requires provenance. Changing a fact creates a successor or explicit new version; old facts remain queryable historically and are never silently overwritten. Current retrieval favors valid, non-superseded, fresh facts. A freshness mismatch invalidates only records depending on that basis. An episodic record may move WARM → HOT when strongly relevant and later return to WARM or COLD without changing its class or identity.

Raw experiences and evidence may have temporary retention. Evidence can be protected when it explains a major decision, security incident, serious regression, rare failure, human correction, or benchmark. Collection is reference-aware and deterministic: evidence must be past its configured minimum age, have a valid extraction receipt when required, and have no direct memory, QA, investigation-hold, protection, or legacy event reference. Retention is disabled until an owner configures an interval. The local maintenance CLI requires confirmation of the exact previewed artifact IDs and archives only Cathulu's URI metadata; it preserves stable IDs and hashes and never deletes external files. Existing immutable event rows that contain raw artifact URIs block collection.

### Bounded activation and provenance-preserving transfer

Each logical context scope has a configurable HOT-memory budget. Main Overseer, project/scope, and worker/task packets receive only their relevant state. When a budget is exceeded, deterministic policy first demotes inactive knowledge from HOT to WARM, consolidates or replaces detail with references when justified, and may route transient detail to evidence retention. Overflow never triggers arbitrary deletion of durable knowledge.

Known-by state is keyed by logical receiver scope and the memory content hash. If the same still-valid version is already known, omit it; if a reminder is useful, send a compact reference; if it changed, send a delta; if invalidated, replace it. Every Cathulu-controlled transfer records its run, sender and receiver scope, memory ID/hash, class and temperature, byte size, observable token count, retrieval method, whether it is new or reintroduced, timestamp, and downstream use when observable. Do not store the transferred prompt body merely to measure context.

Resumption starts from a compact scope snapshot, then checks Git, Graphify, dependency, and contract deltas, invalidates stale knowledge, promotes relevant WARM memories, and sends only changed/relevant context. Transcript replay is not the resumption mechanism. Context-transfer records and memory metadata are the shared foundation; telemetry must populate that ledger rather than introduce a second transfer system.

### Retrieval and maintenance boundaries

Retrieval specializes by source: current exact state from SQLite; named knowledge and errors from SQL/FTS; optional code structure from Graphify; historically similar experience from optional semantic retrieval; large evidence through artifact references. Graphify returns one bounded directed path with current repository-relative source locations, relation, and confidence. It reads only a local code-only export; missing, stale, malformed, or unsupported exports contribute no candidates. Current exact state and SQLite/FTS remain authoritative. After identifying the task scope, load its bounded HOT packet, query exact current state and canonical constraints, then add relevant WARM knowledge from SQL/FTS, Graphify, or optional semantic candidates. Deduplicate, filter already-known content, validate freshness and supersession, fit the result to the scope budget, and record controlled transfers. COLD evidence is never injected automatically. Semantic search, if later justified, returns candidate IDs only; every result resolves to an authoritative SQLite record. Limit semantic candidates primarily to WARM canonical and episodic knowledge. Do not embed raw telemetry, transcripts, full logs, exact current state, dependency edges, or whole Graphify snapshots by default.

The local **Memory Gardener** is deterministic maintenance logic, not a continuously running LLM agent. M4 exposes an explicit manual run that records proposals for inactive HOT demotion, stale-memory demotion, supported episodic promotion, duplicate episodic/evidence memories, duplicate artifact groups, and orphan evidence. Proposals retain their reasons and source IDs; accepted promotion/demotion changes the existing memory row and appends an event. Repeated episodes can be consolidated through a separate explicit operation that creates a reviewable canonical candidate and retains source memory and artifact links. The Gardener never deletes evidence. It suppresses duplicate pending proposals, and safe class/temperature changes are revalidated when reviewed.

Telemetry compaction follows evidence utility rather than a fixed age rule: recent runs may retain bounded full events, older runs can retain a summary and anomalies, and long-term history can retain workflow aggregates, significant run summaries, and protected failures. Before removing raw evidence, verify that useful knowledge, aggregate updates, supporting provenance, and unusual anomalies have been preserved. Duplicate observations are easier to compact than unique explanations for important decisions.

M4 records immutable memory-policy versions and evaluation rows keyed by experiment, task type, and completed Cathulu run. Comparisons report verified outcomes, context bytes, reintroduced bytes, retrieval usefulness, latency, regressions, rework, and human intervention. Storage snapshots are captured after run completion and associate SQLite/WAL size, growth, memory temperature bytes, artifact-reference metadata, duplicate groups, orphan evidence, and logical URI bytes archived with the run/project/workflow. The dashboard shows only compact health signals: HOT/WARM/COLD bytes, HOT scope count and largest scope HOT size, stale and duplicate counts, reuse, transfer reintroduction and amplification, retrieval usefulness, pending proposals, SQLite size/growth, orphan evidence, and logical bytes collected. These sizes describe Cathulu's database and URI metadata, not the size of external files referenced by artifacts.

No semantic index is implemented. M11 adds optional Graphify snapshot validation and invalidation after a measured local pilot; SQLite remains authoritative, and exact-state/SQL/FTS retrieval continues when Graphify is unavailable. M4 does not compact raw telemetry or adapt policy automatically; it supplies versioned measurements and deterministic review points for later experiments.

## Security and privacy baseline

### Protected assets and trust boundaries

- Local repository paths and their Git metadata.
- Durable decisions, objectives, memory, event history, run outcomes, provenance, and quality artifacts.
- Model/tool telemetry that may contain untrusted repository text or sensitive command arguments.
- Codex's approval, sandbox, and permission decisions, which remain owned by Codex.

Repository files and telemetry inputs are untrusted. MCP input is validated and mapped to domain operations. Registered paths are canonicalized and restricted to the explicit registry. No generic SQL operation is exposed. No unnecessary TCP listener is opened. Never treat hooks as an authorization boundary or as proof that a tool succeeded; preserve Codex's sandbox and approval mechanisms for consequential operations.

Do not persist secrets, raw prompts, or full agent transcripts by default. Store structured task fields, provenance links, event type, hashed identifiers, bounded metadata, content hashes, and artifact references. Treat any future prompt or transcript retention as a separate privacy decision. Keep Cathulu's SQLite authority, memory, evidence references, telemetry, indexes, and policy experiments local. If an owner explicitly enables a remote specialist, make the egress visible and send only the smallest sanitized input needed; never send full repositories, secrets, full transcripts, raw Cathulu memory, or entire artifact stores by default. Use OS-local storage permissions, database transactions, idempotent state transitions, and startup reconciliation for recovery. Protect unique provenance conservatively and compact redundant representations only after useful knowledge has been preserved.

## Dashboard interaction contract

The dashboard uses the Operate mode: scan the single persistent-role graph, identify project activity and blockers, and inspect selected evidence through existing MCP resources. The graph shows one Main role, one persistent Project Manager role per registered project, compact context/tool indicators, active assignments, explicitly parented workers, and unlinked hook events where parentage is unknown. A selected Main/PM dossier may expose one pending Owner request at a time with a two-step approve/decline control. The approve/decline control stores human intent only; a separate authorized action and deterministic QA remain necessary.

The user chooses a target for each preview: a registered project's `.codex/config.toml`, the user `config.toml`, a named user profile, or export-only. Project-scoped config is only used by Codex when that repository is trusted. No caller-supplied filesystem paths are accepted. The only dashboard write remains the explicit Owner-action decision in ADR-0018. See [ADR-0002](decisions/ADR-0002-cathulu-hosted-agent-selectors.md) and [PLAN-002](plans/PLAN-002-phase3-codex-delegation.md).

M9 adds SQLite schema v8 preference and applied-target metadata. The local bundled catalog does not prove account/workspace availability. The user must review an exact field-level diff and explicitly apply it. Cathulu uses `toml_edit` to preserve comments and unrelated keys, rechecks file hashes and path boundaries, creates a backup per changed file, and records that the configuration was written. Named-agent preferences update only matching, existing custom-agent TOML files; missing or invalid roles are shown as skipped. Export-only returns selected TOML snippets without reading config contents. These writes are available only through the separate desktop settings surface; MCP cannot write Codex configuration. Cathulu cannot verify that a session loaded a value, so runtime effectiveness remains `unverified`. Tests use disposable files and did not change the owner's Codex config.

Any future optimization-impact view remains read-only and compact, and is added only if real evaluation data makes it useful. It may compare treatment mode, observable context or turn reduction, latency, verified outcomes, QA, regressions, and rework; it must show unknown when a measure is unavailable. It does not become a model-management console or merge with M9 Codex selectors.
