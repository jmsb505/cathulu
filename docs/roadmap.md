## Phase 1 — Instrumentation and state foundation (M1-M3)

Start with the vertical slice in the project definition: local project registration, SQLite persistence, deterministic Git reconciliation, local MCP state reads, read-only dashboard, and automated tests. Extend it with objectives/tasks, decisions, immutable workflow versions, transactional event/state updates, runs, QA evidence, available local Codex telemetry, blockers, recent activity, and restart recovery. Add the memory substrate in this phase: independent class and temperature, stable identity and hashes, provenance, temporal validity and supersession, freshness markers, known-by state, context-transfer records, artifact references, and bounded HOT-memory scopes. This is a schema and deterministic-policy foundation, not a full automatic memory agent.

No worker orchestration or model/effort selectors are included in M1-M3. Codex's supported configuration pathway and role-specific model/effort fields are verified; Cathulu's selector surface is delivered separately in Phase 3 M9.

## Phase 2 — Memory lifecycle and context experiment (M4-M5)

Use the Phase 1 transfer ledger and memory metadata to measure context reintroduction, amplification, reuse, retrieval usefulness, and storage growth. M4 delivers selective SQL/FTS retrieval, a manual deterministic Memory Gardener for duplicate detection and reviewable promotion/demotion proposals, explicit provenance-linked consolidation candidates, extraction receipts, conservative reference-aware archiving, policy experiments, and storage/health metrics. Unique provenance and protected evidence remain traceable; retention stays configurable and disabled until an owner sets a minimum age. Later work may add summary/aggregate maintenance, telemetry compaction, or semantic indexing if usage and measured retrieval gaps justify them; any semantic index must return candidate IDs while SQLite remains authoritative. Graphify invalidation waits for a real graph snapshot source.

## Phase 3 — Codex-native worker delegation (M6-M9)

Reuse native Codex subagents and worktrees. M6 adds bounded typed task packets, hashed idempotency/correlation metadata, scope-checked memory and artifact links, and append-only delegation lifecycle events; it records owner handoff state without spawning agents. M7 adds structured worker reports and read-only dashboard presentation; M8 adds verifiable worktree isolation and supported worker telemetry. M9 adds a separate model/effort settings surface with explicit project, user-base, profile, and export-only targets; safe TOML preview/apply; preserved backups; and honest stored/written/effective status. Detailed milestones are in [PLAN-002](plans/PLAN-002-phase3-codex-delegation.md).

## Phase 4 — Durable scoped context (M10)

Add scopes and Sub-Overseers only after telemetry shows repeated cross-project reconstruction whose measured cost exceeds context maintenance and coordination overhead. Detailed entry evidence and acceptance criteria are in [PLAN-003](plans/PLAN-003-evidence-gated-scaling.md). No qualifying recurring cross-project workflow is currently available, so M10 is not eligible for the current work pattern. Backlog: exercise and evaluate a cross-repository handoff when real work naturally spans repositories; do not create a synthetic task for it. This deferred check does not block unrelated validation or maintenance, and M12-M14 retain their separate real-run evidence gates.

## Phase 5 — Graphify (M11; validated)

Integrate structural retrieval read-only, record graph snapshot identities/deltas, invalidate only memories tied to changed graph bases, and benchmark selected neighborhoods against simpler file/FTS retrieval. Graphify is a retrieval/freshness source, not a second memory authority. M11 completed on 2026-10-21: its local-only evidence gate passed using Graphify 0.9.82, schema 1, code-only extraction, and a pre-registered three-task comparison. Cathulu exposes bounded MCP path retrieval, SQLite snapshot identity/freshness, and selective graph-memory invalidation; the implementation passed Windows workspace tests and the local MCP release build. Validation evidence is in [PLAN-003](plans/PLAN-003-evidence-gated-scaling.md), with the source contract in [ADR-0006](decisions/ADR-0006-local-graphify-snapshot-contract.md).

## Phase 6 — Convergence (M12)

Add quality-distance vectors, state signatures, loop/stall/oscillation/regression detection, and escalation/replanning after enough run evidence exists. Keep M12-M14 gated on real, comparable run data as defined in [PLAN-003](plans/PLAN-003-evidence-gated-scaling.md).

## Phase 7 — Workflow experiments (M13)

Aggregate comparable runs by task class and workflow version; propose, review, and version workflow changes; compare future outcomes.

## Phase 8 — Adaptive policy research (M14)

Consider learned routing or automatic scope/policy changes only after enough trustworthy repeated data exists. Reinforcement learning and automatic policy changes are outside the MVP.

## Phase 9 — Optional specialist-model optimization (M15-M18b merged; M18-M19 evidence-gated)

Evaluate narrow DecisionModel and ContextModel capabilities as optional optimization layers around the current Cathulu/Codex workflow. This phase does not replace Codex or introduce a required hosted service. Every capability defaults to disabled; shadow mode records predictions without changing execution. M9's Codex model/effort selectors remain separate. Existing SQLite run, workflow, event, memory-policy, and artifact authorities must be reused before any additive schema is proposed.

- **M15 — Provider-neutral contracts and attribution (merged to `main`):** define versioned DecisionModel/ContextModel contracts, disabled behavior, independent per-capability and per-workflow modes, immutable per-run treatment attribution, and local invocation telemetry. Existing append-only events provide the authority, so no schema migration was required. Invalid optional configuration falls back to all-disabled; no provider adapter or model call is included.
- **M16 — DecisionModel shadow trials (local mechanics validated):** add fixed workflow/delegation outcome schemas with escapes, a compact SQLite-derived routing-state projection, strict bounded result validation, local-only shadow invocation attribution, and post-run human review linked to final QA/run events. Tests use a deterministic double; they do not demonstrate model value. TypeSafe's direct API and data-handling documentation were reviewed; requests are not used for training, but service/telemetry processing and retention terms require owner review before any remote call. No adapter or remote call is included.
- **M17 — ContextModel shadow extraction (local mechanics validated):** read only registered local test/compiler/CI/tool-output artifacts, verify recorded hashes, select bounded error-adjacent spans, and pass a stable Cathulu artifact reference without exposing filesystem paths. Candidate quotes must match exact source bytes. The raw artifact stays retrievable; results and measurements are append-only shadow evidence and never change execution. Tests include a captured local Rust test-harness failure and deterministic doubles. ScaleDown's official client documents remote compression, but extraction semantics and request-retention terms were not verified; no provider is integrated or evaluated, so product value is unknown.
- **M18a — Provider-connectivity readiness (merged to `main`):** add disabled-by-default Jev routing and ScaleDown extraction adapters, local key loading, explicit per-run remote consent, bounded requests, safe failure recording, and local mock HTTP contract tests. A follow-up public MCP test drives both tools with credentials absent and confirms skipped, attributed invocations leave run/QA and source evidence unchanged. All checks remain local; no live provider calls are claimed. Comparative M18 scoring remains ineligible until representative Cathulu runs establish a baseline; active treatment remains separately gated.
- **M18b — ScaleDown response-contract correction (merged to `main`):** align the requested JSON schema with the parser's required exact-span entity shape and reject responses that omit `entities`. The regression test validates local schema/parser consistency; live-provider compatibility and extraction quality remain unverified.
- **M18 — Controlled ablation and evidence review:** after shadow safety and quality checks, seek explicit owner approval for a reversible pilot. Compare baseline (all specialists disabled), decision-only, context-only, and both under the same workflow version, task strata, completion criteria, and QA gates. Set sample/decision criteria from observed baseline variation; do not use arbitrary counts or treat synthetic tests as product evidence. Two shadow integration runs are recorded, including one independent PULSO local QA task, but no matched cohort or representative baseline exists, so comparative scoring is not eligible yet. Any active treatment still requires explicit owner approval; no automatic promotion follows.
- **M19 — Evidence-backed capability proposals:** evaluate one additional capability at a time, such as compression, summarization, classification of large unstructured inputs, post-retrieval memory reranking, scope activation, or secondary convergence classification. Keep exact retrieval and deterministic convergence authoritative. Present measured enable/disable suggestions for owner review; do not rewrite orchestration policy automatically. Consider a compact read-only impact view only if real data makes it useful.

M15 can be planned independently of M10 and the M12-M14 real-run gates. M16-M19 use the existing M4 run, transfer, memory-policy, and storage measurements where applicable. The deferred cross-repository handoff check remains a backlog item for naturally occurring work and is not a prerequisite for this phase.

## Phase 10 — Bounded per-project agent hierarchy (M20-M21 verified; M22-M24 implementation reconciled; final validation and M25 task deferred)

Main Overseer coordinates only; it does not perform repository implementation. Each project has a persistent logical Project Manager role and at most one active task assignment, and each assignment may dispatch at most two workers total. Every role uses Cathulu's existing scoped memory, known-by, context-transfer, delegation, and evidence operations. M20 records the role and memory contract. M21 verified nested PM-to-Worker spawning and Cathulu MCP reachability in the target Codex client using repository-free run 4 (`verified_success`). M22-M24 source from the schema-11 snapshot has been reconciled into the tracked checkout, including hierarchy parentage/caps, memory activation receipts, and the read-only project snapshot. Schema 12 in M27 adds one durable Main/PM role record and stable context scopes; replacement chats reuse those scopes. The updated graph shows persistent role seats, explicit children, and unlinked hook evidence without inferring parentage. The full Rust/UI suites pass, and the matching Windows pair is published behind the stable Codex path. Native graph/window review remains pending, and M25 waits for a real independent project task. The M21 probe still shows differences in available PM/Worker tools and no native chat identity; a tool-profile key is configuration metadata, not proof of runtime availability. SQLite enforces one logical Main row, but without a native chat identity or lease Cathulu cannot know which of multiple chats is currently acting as Main. This work is separate from M10's cross-project scope/reconstruction evidence gate, and no synthetic cross-repository task is required. See [ADR-0009](decisions/ADR-0009-bounded-project-agent-hierarchy.md), [ADR-0011](decisions/ADR-0011-persistent-logical-agent-roles.md), [agent operating contract](agent-operating-contract.md), and [PLAN-006](plans/PLAN-006-bounded-project-agent-hierarchy.md).

## Phase 11 — MCP-linked desktop startup (M26)

Pair the current MCP and desktop release binaries so starting Cathulu MCP opens the local support dashboard without activating it or interrupting typing. Repeated starts leave an existing window as-is. The canonical build script stages and hashes a matched pair, stores it in an immutable source-fingerprinted directory, and advances the stable `target/mcp-current` junction configured in Codex. The desktop release uses Tauri's `custom-protocol` feature to load bundled `frontendDist`; it does not depend on a running development server. Startup remains fail-open, and dashboard/MCP communication uses the same local store. The current already-running MCP process still needs a controlled restart to load the published pair. See [PLAN-007](plans/PLAN-007-mcp-desktop-autolaunch.md) and [ADR-0010](decisions/ADR-0010-launch-dashboard-with-mcp.md). Visual dashboard and live reconnection verification remain open.

## Phase 12 — Persistent logical agent roles (M27)

Persist exactly one Main Overseer and one Project Manager role for each registered project, independently from Codex chats, runs, and temporary task assignments. Keep role-owned memory and tool-profile keys stable so replacement chats reuse the same context and known-by state. PM memory activation must use the role's stable receiver scope and dispatch rechecks that binding. The one read-only graph always shows the persistent roles, recorded active assignments, explicitly parented workers, and hook events whose parent remains unknown. SQLite continues to own the role catalog; actual Codex chat identity and tool availability remain unclaimed until observable. The database has one Main role, but the current Codex integration provides no chat identity or exclusive occupant lease to identify which open chat is acting as Main. Automated checks pass and the matching Windows release is published behind the stable Codex path; native visual review and live MCP reconnection remain pending. See [ADR-0011](decisions/ADR-0011-persistent-logical-agent-roles.md) and [PLAN-008](plans/PLAN-008-persistent-logical-agent-roles.md).
